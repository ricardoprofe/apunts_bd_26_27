Unitat 2.5. Normalització de bases de dades

El model relacional consisteix a disposar d'un conjunt de taules de qualitat: han de respectar els requeriments inicials i evitar redundàncies innecessàries. La manera ideal d'aconseguir-ho és partir d'un esquema Entitat-Relació (E-R) correcte.

Tanmateix, de vegades l'analista no elabora un diagrama E-R, sinó que crea directament uns primers esbossos de les taules. Aquestes taules poden contindre redundàncies i altres problemes de disseny. En aquest cas, cal aplicar la normalització: un conjunt de tècniques per a transformar taules mal dissenyades en taules de qualitat.

Aquest problema també es dona quan es parteix d'una importació de dades d'una altra aplicació, que no ha estat dissenyada amb el model relacional, com per exemple fulls de càlcul, fitxers de text, etc.

La normalització és la tècnica del model relacional que augmenta gradualment la qualitat de les taules.

La normalització permet determinar:

  • Quines taules falten o sobren.
  • Quines claus i atributs ha de tindre cada taula.
  • Quines relacions hi ha entre les taules, representades mitjançant claus alienes.

1. Dependències funcionals

Suposem que un analista ha de dissenyar una base de dades per a una biblioteca. Entre els requeriments s'indica el següent:

«Necessitem un llistat de llibres on aparega el codi del llibre, el títol, el nombre de pàgines, el codi de l'autor, el nom de l'autor i la seua data de naixement.»

L'analista no ha elaborat l'esquema E-R i ha creat directament la taula següent:

1
LLIBRES = codi + títol + num_pàgines + codi_autor + nom_autor + data_naix_autor

Aquest disseny presenta un problema: totes les ocurrències de LLIBRES que tinguen el mateix codi_autor també tindran el mateix nom_autor i la mateixa data_naix_autor. Per tant, aquestes dades es repetiran en molts registres.

Això ocorre perquè, donat un codi_autor, només hi ha un nom_autor i una data_naix_autor. En altres paraules:

1
codi_autor -> nom_autor, data_naix_autor

Es diu que codi_autor determina nom_autor i data_naix_autor, o que aquests dos atributs depenen funcionalment de codi_autor.

Per a evitar la redundància, podem separar les dades dels autors en una altra taula:

1
2
3
4
LLIBRES = codi[PK] + títol + num_pàgines + codi_autor[FK]
C. Ali: codi_autor -> AUTORS(codi)

AUTORS = codi[PK] + nom + data_naix

Sense haver desenvolupat encara tota la teoria, en aquest exemple ja s'ha aplicat un pas de normalització.

1.2. Definició de dependència funcional

Siga la relació:

1
T = A[PK] + B + C + ...

Es diu que un atribut X depén funcionalment d'un altre A, quan cada valor de A té associat un únic valor de X en la taula T.

Es representa així:

1
A -> X

Exemple: préstecs de biblioteca

Suposem que es vol guardar informació sobre préstecs de biblioteca amb aquesta taula:

1
PRÉSTECS = (codi_llibre + num_soci)[PK] + data + títol + nom_soci
Codi de llibre Núm. de soci Data Títol Nom del soci
HOMMAN 111 11-03-2017 L'home manuscrit Pep Garcia
DONQUI 111 11-03-2017 Don Quijote de la Mancha Pep Garcia
HOMMAN 222 09-04-2017 L'home manuscrit Maria Burguera
DONQUI 111 07-04-2017 Don Quijote de la Mancha Pep Garcia
DONQUI 222 08-04-2017 Don Quijote de la Mancha Maria Burguera

Si s'introdueixen dades amb aquest disseny, el títol es repetirà sempre que aparega un mateix codi de llibre, i el nom del soci es repetirà sempre que aparega un mateix número de soci.

Les dependències funcionals serien:

1
2
3
codi_llibre -> títol
num_soci -> nom_soci
(codi_llibre + num_soci) -> data

Després de normalitzar, podem obtindre les taules següents:

1
2
3
4
5
6
7
PRÉSTECS = (codi_llibre + num_soci)[PK] + data
FKs:
- codi_llibre -> LLIBRES(codi)
- num_soci -> SOCIS(codi)

LLIBRES = codi[PK] + títol
SOCIS = codi[PK] + nom

Dades després de normalitzar:

2. Formes normals

Les formes normals són les propietats que han de complir les relacions o taules. El procés de normalitzar una relació consta de les fases següents, en aquest ordre:

  1. Passar la relació a primera forma normal (1FN) i, si cal, optimitzar les claus.
  2. Passar la relació a segona forma normal (2FN).
  3. Passar la relació a tercera forma normal (3FN).
  4. Passar la relació a forma normal de Boyce-Codd (FNBC).
  5. Passar la relació a quarta forma normal (4FN).
  6. Passar la relació a cinquena forma normal (5FN).

Si una relació està en 3FN, també compleix 1FN i 2FN. En aquest tema es treballarà principalment fins a la 3FN. La resta són menys freqüents.

2.1. primera forma normal (1FN)

Una taula està en 1FN si no té atributs multivalents ni dependències funcionals entre els components de la clau.

De manera informal, una taula està en 1FN si:

  • No té grups repetitius, representats com {...}.
  • No té dependències funcionals de dins a dins de la clau composta.

Fase 1.1: eliminar atributs multivalents

Una relació no està en 1FN si té un atribut multivalent. Per exemple:

1
PERSONES = dni + nom + data_naix + {telèfon}

El problema és que una persona pot tindre un nombre variable de telèfons, de manera que no es pot reservar un nombre fix de columnes per a aquests valors.

Exemple de disseny no normalitzat:

DNI Nom Data de naixement Telèfon 1 Telèfon 2 Telèfon 3
111 Pep 04-03-1970 555111222 555111333 555111777
222 Pepa 05-06-1979 555222555 555222666

La solució és separar els telèfons en una altra taula:

1
2
3
PERSONES = (dni[PK] + nom + data_naix)

TELEFONS = ((telèfon + dni[FK])[PK])

La clau primària de TELEFONS estarà formada inicialment per dni + telèfon.

Exemple de dades normalitzades:

DNI Nom Data de naixement
111 Pep 04-03-1970
222 Pepa 05-06-1979
DNI Telèfon
111 555111222
111 555111333
111 555111777
222 555222555
222 555222666

Fase 1.2: optimitzar claus

Si una relació té una clau composta, s'ha de comprovar si és possible reduir el nombre de camps que formen la clau. Per a això s'han d'eliminar les dependències funcionals entre els camps de la clau composta.

En l'exemple anterior:

1
TELEFONS = dni + telèfon

La clau composta dni + telèfon significa inicialment que:

  • Una persona pot tindre molts telèfons.
  • Un telèfon pot correspondre a moltes persones.

Però si els requeriments indiquen que un telèfon només pot pertànyer a una persona, tenim la dependència funcional:

1
telèfon -> dni

Aquesta és una fletxa de dins a dins de la clau. Això indica que la relació encara no està realment en 1FN: s'havia definit una relació N:M quan en realitat era 1:N.

La clau s'ha d'optimitzar i el resultat és:

1
TELEFONS = (telèfon[PK] + dni[FK])

On telèfon passa a ser la clau primària.

Exercicis sobre la 1FN

1: Normalitza la relació:

1
CLIENTS = codi + nom + {tel}
codi nom tel
001 John 123456, 789654
002 Jane 456345
003 Bob 789123, 321546, 897678

2: Normalitza la relació anterior si un telèfon només pertany a un client.

3: Normalitza la relació:

1
CLIENTS = codi + nom + {tel + operadora}
codi nom tel + operadora
001 John 123456 + Movistar, 789654 + Vodafone
002 Jane 456345 + Orange
003 Bob 789123 + Movistar, 321546 + Vodafone, 897678 + Orange

Restricció d'integritat: un telèfon només treballa en una operadora.

4: Normalitza la relació anterior si un telèfon només pertany a un client i només treballa en una operadora.

2.2 segona forma normal (2FN)

Definició

Una taula està en 2FN si està en 1FN i tot atribut no clau depén de tota la clau, i no només d'una part.

Per tant, només són sospitoses de no estar en 2FN les taules amb una clau principal composta.

Exemple general d'una relació que no està en 2FN:

Aquesta relació no està en 2FN perquè té una dependència y -> b que ix d'una part de la clau composta i arriba a un atribut que no forma part de la clau.

Com passar a 2FN

La solució és igual que en el cas d'optimització de claus de 1FN:

  1. Eliminar de la relació original el destí de la fletxa.
  2. Crear una nova relació amb l'origen i el destí de la fletxa.
1
2
3
A = ((x + y)[PK] + a)

B = (y[PK] + b)

Exemple: notes d'alumnes

Taula inicial:

codi_assig n_exp nota nom_alumne
BD 111 7 Pep Garcia
PRG 111 8 Pep Garcia
BD 222 9 Maria Burguera
FOL 111 7 Pep Garcia
PRG 222 8 Maria Burguera

La clau està formada per codi_assignatura + num_expedient, però nom_alumne depén només de num_expedient:

Això genera redundància, ja que el nom d'un alumne es repeteix en totes les seues notes. També podria generar incoherències si, per error, s'escriuen noms diferents per al mateix expedient.

Solució:

1
2
3
NOTES = ((codi_assignatura + num_expedient[FK])[PK] + nota)

ALUMNES = (num_expedient[PK] + nom_alumne)

Exemple de resultats:

Codi d'assignatura Núm. d'expedient Nota
BD 111 7
PRG 111 8
BD 222 9
FOL 111 7
PRG 222 8
Núm. d'expedient Nom de l'alumne
111 Pep Garcia
222 Maria Burguera

Exercicis sobre 2FN

  1. Normalitza la relació:

    1
    COMPRES = ((article + data)[PK] + preu + proveïdor)

    Restricció d'integritat: un article només es pot comprar a un proveïdor.

  2. Normalitza la relació:

    1
    R = ((a + b + c)[PK] + d)

    L'atribut d depén només de b + c.

  3. Normalitza la relació:

    1
    ESCRIURE = ((codi_autor + codi_llibre)[PK] + editorial + data_pub + nom_autor + nom_llibre)
    codi_autor codi_llibre editorial data_pub nom_autor nom_llibre
    001 111 Planeta 01-01-2020 Cervantes Don Quijote
    001 112 Plaza&Janes 01-01-1998 Cervantes Don Quijote
    003 222 Planeta 01-01-2020 Orwell 1984
    003 333 Planeta 01-01-2015 Orwell Animal Farm
    002 444 Crítica 01-01-2012 Shakespeare Hamlet
    003 335 Planeta 01-01-1987 Orwell Animal Farm

2.3 tercera forma normal (3FN)

Definició

Una taula està en 3FN si està en 2FN i cap atribut no clau —ni principal ni alternatiu— depén d'un altre atribut no clau.

De manera informal, una taula està en 3FN si està en 2FN i no té fletxes de fora a fora de la clau.

Exemple general:

La relació no està en 3FN perquè b i c són atributs que no formen part de la clau, i c depén de b.

Com passar a 3FN

  1. Eliminar de la relació original el destí de la fletxa.
  2. Crear una nova relació amb l'origen i el destí de la fletxa.
1
2
A = x + a + b
B = b + c

Exemple: poblacions i codis postals

Taula inicial:

1
PERSONES = (dni[PK] + nom + codi_postal + població)
dni nom codi_postal població
111 Pep Garcia 46701 Gandia
222 Maria Burguera 46720 Bellreguard
333 Manolo Vendrell 46701 Gandia
444 Carles Ventura 46701 Gandia
555 Andreu Albors 46430 Sollana

La taula no està en 3FN perquè població depén de codi_postal i cap dels dos atributs és una clau alternativa:

1
codi_postal -> població

Això genera redundància: cada vegada que apareix el codi postal 46410, es repeteix que correspon a Sueca.

Solució:

1
2
PERSONES = (dni[PK] + nom + codi_postal[FK])
POBLACIONS = (codi_postal[PK] + població)
dni nom codi_postal
111 Pep Garcia 46701
222 Maria Burguera 46720
333 Manolo Vendrell 46701
444 Carles Ventura 46701
555 Andreu Albors 46430
Codi postal Població
46701 Gandia
46720 Bellreguard
46430 Sollana

3. Eliminar altres redundàncies

A més de les formes normals, cal revisar altres redundàncies que puguen aparéixer.

3.1. Eliminar redundàncies intrataula

S'eliminen els camps que es poden obtindre a partir d'altres camps de la mateixa taula.

Exemple:

1
NOTES = dni + assignatura + nota1 + nota2 + nota3 + nota_mitjana

Es pot eliminar nota_mitjana perquè es pot calcular a partir de les altres notes:

3.2. Eliminar redundàncies intertaula

S'eliminen els camps que es poden obtindre a partir de camps d'altres taules.

Exemple:

1
2
NOTES = dni + assignatura + nota
ALUMNES = dni + nom + nota_mitjana

nota_mitjana es pot calcular a partir de les notes de la taula NOTES, sumant-les i dividint el resultat pel nombre d'assignatures.

Tanmateix, l'eliminació de redundàncies intertaula pot alentir les consultes. Per això cal trobar un equilibri entre la puresa del disseny i l'eficiència de l'aplicació.

3.3. Fusionar taules amb la mateixa clau

Es poden fusionar taules que comparteixen la mateixa clau, sempre que no es perda la informació sobre opcionalitat o especialització obtinguda en les fases anteriors.

Exemple:

1
2
ALUMNES_DADES_PERSONALS = codi_alumne + nom + data_naix + telèfon
ALUMNES_DADES_ACADÈMIQUES = codi_alumne + curs + grup + repetidor_sn

Es poden fusionar en:

1
ALUMNES = codi + nom + data_naix + telèfon + curs + grup + repetidor_sn

4. Esquema resum de com normalitzar

Forma normal No està en aquesta forma si té... Com es transforma
1FN Atributs multivalents {...} S'elimina el grup repetitiu i es crea una nova relació amb la clau de la taula original i l'atribut multivalent.
1FN Fletxa de dins a dins de la clau S'optimitza la clau. Si la DF afecta tota la clau, el destí deixa de ser clau; si no l'afecta, se separen origen i destí en una nova taula.
2FN Fletxa de dins a fora de la clau S'elimina el destí de la fletxa de la taula original i es crea una altra taula amb origen i destí.
3FN Fletxa de fora a fora de la clau S'elimina el destí de la fletxa de la taula original i es crea una altra taula amb origen i destí.

6. Exemple de normalització

A continuació es mostra un procediment general per a resoldre exercicis de normalització.

Exemple: factures i articles

Volem normalitzar les relacions:

1
2
3
FACTURES = num + codi_client + dni + nom + tel_client + data + {línia + article + descripció + preu + quantitat}

ARTICLES = codi + descripció + família + descripció_família

Pas 1: establir suposicions

  • En una factura no poden haver-hi dues línies amb el mateix article.
  • El preu és sempre el mateix per a cada article.
  • Es poden establir altres suposicions si els requeriments no ho especifiquen.

Pas 2: detectar dependències funcionals

En FACTURES:

1
2
3
codi_client -> dni, nom, tel_client
article -> descripció, preu
num + línia -> article, quantitat

En ARTICLES:

1
família -> descripció_família

Pas 3: normalitzar cada taula

De FACTURES obtenim:

C. Ali: codi_client -> CLIENTS(codi_client)

C. Ali:
- num -> FACTURES(num)
- article -> ARTICLES(article)

ARTICLES_1 = article + descripció + preu

CLIENTS = codi_client + nom + telèfon

De ARTICLES obtenim:

C. Ali: família -> FAMILIES(família)

FAMILIES = família + descripció

Pas 4: obtindre l'esquema integrat final

Cal fusionar les taules que tinguen la mateixa clau, sempre que no representen una especialització, i establir noms coherents per a les taules i els atributs.

L'esquema final seria:

14
FACTURES = num + codi_client + data
C. Ali: codi_client -> CLIENTS(codi_client)

LINIES_FACTURA = num + línia + article + quantitat
C. Ali:
- num -> FACTURES(num)
- article -> ARTICLES(article)

ARTICLES = article + descripció + preu + família

FAMILIES = família + descripció

Pas 5: dibuixar el graf de dependències entre taules

El graf de dependències indica l'ordre en què s'haurien de crear les taules d'acord amb les claus alienes:

1
2
FAMILIES -> ARTICLES -> LINIES_FACTURA
CLIENTS -> FACTURES -> LINIES_FACTURA
